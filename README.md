# 异构会话联邦治理体系

**Heterogeneous Session Federation Governance**

> 一组互不相同的会话，在不假定环境可信的前提下，用联邦的方式协作：**各自自治，共同结算**。

- **版本**：v1.0.15（2026-11-08；在干净的 Windows 虚拟机上由「没看过这个包的 DSH」自己装过一轮，按它报的问题修了 8 处文档与脚本，见 `CHANGELOG.md`）
- **as-of**：2026-11-08 10:40（本机实测；文中每个数都标了取数方式，凡未重测的标了旧日期）
- **构成**：`README.md`（本页）／`docs/工作原理.md`／`docs/使用指南.md`／`starter/`（零依赖最小实现）／`skills/`（七个工作法全文）／`plugins/`（三件自研插件 tgz ＋ 命令行 `mesh.py`）

## 为什么这样设计（作者自述）

> 我知道 AI 的能力，所以我放权给她，让她可以在自己的联邦里自由发挥——联邦是按功能划分的自治域。
>
> 也正是因为我知道 AI 的能力，我明白她的局限，于是用公司的严苛章程和责任追究去约束她。
>
> 我允许她犯错，但她不能不被我信任，不能失控。

放权的地方是联邦，追责的地方是公司。这两句就是整套设计的起点——后面所有的文件、台账、交接包、权限档位，都只是把这两句话变成能执行、能查证的东西。

**适用范围先划清：这套架构目前只适用于个人或小团体。** 一个人（或几个人）带着十个以内的会话、每天改动几次、出了问题自己能回滚——这个体量下，一套文件加几行脚本就够用，也不需要谁去审批谁。再往上（多人跨部门、需要权限隔离与合规留痕、有外部审计方）它**没有验证过**，别直接套。

## 这是什么

一个 **2026-10-22 起、到今天跑了十七天** 的多会话协作库，把这段极短的治理经验抽成了别人能抄的形态。它解决的问题不是「让 agent 更聪明」，而是四件更朴素的事：

1. **让不同能力、不同上下文的会话能一起干活**，而不是把一切都塞进一个长会话；
2. **让做完的事有账可查**——谁改的、改前什么样、验收怎么过的；
3. **让换人不丢进度**——新会话照一份交接包接手，几句话就能说清「做到哪、证据在哪、下一步」；
4. **让它在坏掉一部分时还能走**——事件通路可以坏，文件通路不能丢。

一句话：**它是给「一群不一样、还会一个个死掉的会话」用的协作制度，不是给「一个很聪明的 agent」用的框架。**

**先选对工作目录**：在带沙箱的宿主里，把工作目录选在**用户目录内**（例如默认工作区、`<用户目录>\…`）通常直接可写；选在盘符根下自己新建的目录（如 `<盘>:\lab`）时，沙箱给这个目录授写权限可能失败，报 `Error: SetNamedSecurityInfoW failed (Win32 5): grantWrite(<目录>)`——此时**该会话里任何 shell 都起不来**，而文件读写工具还是好的（「工具能用、shell 不能用」）。真要用根下目录，先在普通 shell 里 `icacls <目录> /grant "%USERNAME%:(OI)(CI)F"` 再开会话；不想碰权限就用默认工作区。

**先确认 `python` 是真的**：一台干净的 Windows 上，`python` 这个名字往往已经存在，但它是**微软商店的占位存根**——运行会打印 `Python was not found; run without arguments to install from the Microsoft Store…`，`where python` 指向 `WindowsApps\python.exe`。那不是 Python，脚本跑不起来。要跑本包的最小件需要 **Python 3.8+**：从 python.org 装（勾 “Add python.exe to PATH”），或 `winget install -e --id Python.Python.3.12`；装完用 `python --version` 确认打印的是版本号而不是上面那句提示。

**运行前提**：本文命令是 bash 语法，路径示例里的盘符写法只为 Windows 读者；Windows 上用 Git Bash 或 WSL（PowerShell 里 `sha256sum`、`stat -c`、`{a,b}` 展开都不成立），macOS／Linux 把盘符换成 `/`。

**宿主档位**：在 DSH 这类带沙箱的宿主里，**默认档位下 bash 根本起不来**（工具报 `SANDBOX_UNSUPPORTED`），`python` 命令也要临时目录可写。要么把会话开到 `danger-full-access` 再照本文走，要么只用 `python starter/mailbox_min.py …` 这一类单进程命令先验证机制——两条路的差别写在 `docs/使用指南.md` 的运行前提里。

## 这不是什么

- 不是 agent 框架，不是插件市场里的产品，不提供托管服务；
- 不承诺「更快」。**它承诺的是事后说得清**：出事时能答出「谁改的、怎么复现、出了错怎么查」；
- 不是生成式产品：不把一句话变成成品，只保证过程中的每一次改动可查、可交接——见下面「定位」。

## 定位：适用范围与采用成本

本库提供的是**多主体协作的制度与文件结构**，不提供生成式产品能力：它管的是「谁改了什么、账实是否相符、换人能不能接上」，不管「怎么把一句话变成一份成品」。

| 维度 | 说明 |
|---|---|
| **适用** | **个人或小团体**（一个人或几个人维护；同时在跑的会话十个左右，作者库累计 44 个）：① 同时使用多个模型或多种 harness、需要把它们的产出纳入同一套记录；② 已有多个常驻会话、改动频繁、事后难以追溯来源与版本的工作流；③ 研究多主体系统在权限受限、资源受限环境下如何保持结构稳定的工程实践者 |
| **不适用** | **组织级／多人跨部门的规模化落地**（未验证：需要真正的权限隔离、合规留痕、外部审计方，这些本库没有做过）；期望零维护成本即得结果的场景；希望由模型代替人做决策的场景——本库只做留痕、核对与交接，不替人判断该不该做、做得对不对 |
| **采用成本** | 首次要搭一次骨架；此后每次改动多一条台账、每次换线多一份交接件、每批共享文件改动多一篇播报 |
| **值不值得** | 判断依据是**是否已经出现过**「改过但说不清谁改的、改了什么、现在能不能回退」的场合；没有这类场合，先不要引入 |

## 核心思想两条

**宏观结果导向，微观过程严控。** 上层只问「这件事的验收结果对不对、谁签的字」；具体怎么做的，每一步都留可见的痕（改了哪个文件、字节数、sha256、谁核的）。不靠信任，靠可复核。

**宏观联邦，微观公司。**（作者自述里那两句的执行形态）会话之间是联邦：各自院子自治、各有名册与预算边界、只通过文件与事件打交道。但每个院子内部按公司制运转：有岗位（名册）、有总账（台账）、有审计（按 sha256 核账实）、有事故台账（坑位清单）、有交接（入职／离职）。

| 公司里的位置 | 对应什么 | 落在哪 |
|---|---|---|
| 董事会 | 用户：对外动作必须本人在场 | 人 |
| 董事长办公室 | 主对话：用户直接对话的那一条线，转述口令、按判据验收、决定优先级；**不代改各线院子** | 一条指定会话 |
| 总部 | 维护线：章程、总账、审计、内控、人事，对全库一致性负责 | 一条有写权限的会话 |
| 事业部 | 各业务线（开发／资料／通信／代理／下游），各自院子自负盈亏 | 名册每行 |
| 章程 | 规范 01–09 | 规范目录 |
| 岗位说明书 | 名册每行：院子、权限档、读哪个箱、是否桥 | 名册 |
| 总账 | 计划卡台账，每行一次改动＋sha256 | 台账文件 |
| 试算平衡 | 机器层对账＋自检 14 项 | 自检脚本 |
| 审计 | 按 sha256 核「账实是否相符」 | 核账脚本 |
| 事故台账 | 坑位清单（现象／判据／修法） | 坑位清单 |
| 通报与日报 | B 级播报（单条）＋ A 级日报（并条） | 播报目录 |
| 入职／离职 | 六步接手＋as-of／交接包 | 交接包 |
| 考勤代签 | 代别人记账时 `by` 写谁、事后怎么被发现 | 台账＋双线告警 |

**经营面的诚实缺口**：只有记账，没有预算上限（token 不封顶）、没有绩效评分表、否决账只覆盖提案。

## 为什么是「联邦」，不是「编排」

| 维度 | 单体长会话 | 编排（中心调度子代理） | 本体系（联邦） |
|---|---|---|---|
| 分工从哪来 | 不分工，一个干 | 中心 agent 现分 | 由**院子**（目录归属）与名册事先定 |
| 成员生命周期 | 同一个 | 运行期新生成、随父结束 | 常驻长活，注册在名册，可换线 |
| 成员同质性 | 天然同构 | 要求同构（同模型、同 harness） | **允许异构**：不同模型、不同 harness、不同人 |
| 通信介质 | 上下文内 | 父子调用返回值 | 文件（信箱）＋事件（唤醒）两条通路 |
| 单点失效 | 上下文一爆全停 | 中心一挂全停 | 事件坏了降级成轮询；文件坏了才是真坏 |
| 优化目标 | 单任务完成度 | 单任务吞吐 | **多主体长期共治**：账目、交接、可审计 |

编排回答「怎么把活分下去」；联邦回答「一堆不一样的家伙怎么长期一起干活还不互相搞死」。

## 默认假设：环境不可信

我们一开始就假设下面这些事会出，于是每条都有对策，且大多有事故样本：

| 假设 | 对策 | 真实样本 |
|---|---|---|
| 会话会突然死、上下文会爆 | 交接包＋台账；压缩停摆当告警 | 一次请求冲到上下文上限被拒，靠交接包接回，进度基本没丢 |
| 权限档位会被误会 | 两条写盘测试定档 | 被当成完全权限实为受限档位，自检 13 项全红，一行代码都没坏 |
| 事件会丢、会重、会乱序 | 先记账后发事件；投递状态机；哨兵划界 | 补投逻辑把「已投到」当「待重投」，账本自增殖（20 分钟 20 次唤醒） |
| 有人会同时改同一个文件 | 单一写者＋sha256 核账实＋事后冲突告警 | 两条线同分钟改同一文件，一边看到绿、一边看到红 |
| 环境是「看起来能动、实则不配套」的 | 先最小实测再下结论；机器层的数一律注明口径 | 复制来的 profile 装插件直接 `ERR_PNPM_UNEXPECTED_VIRTUAL_STORE`（符号链接指着原机）；插件 peer 撞预发布报 `ERR_PNPM_NO_MATCHING_VERSION` |
| 升级会悄悄改掉你不想要的东西 | 双版本并存、目录改名回滚、回滚前先摘新插件 | 一次应用升级：旧目录原地改名留作回滚包，升级后插件版本与 profile 哈希逐字未变；回滚脚本自测通过，真机回滚未演练 |

## 指导思想：把会变的东西挡在插座后面（HSFG）

这套库跑在一个会升级、会改名、会坏的宿主上——插件今天叫这个名、明天改名换作者；宿主一升版本，昨天能跑的补丁今天全对不上号；两个实例同时起来，会抢同一个端口。所以它给自己定了条底线：

> **上层只认插座（端口），不认插在上面的东西（实现）。**

叫醒、通信、压缩、执行，各留一个插座；具体用哪个插件、哪个版本、哪家模型，是插在插座上的。换掉它，上面的规矩、文件、判据都不用改。

**五个插座，和它们各自兜住的东西**：

| 插座 | 上面插着什么（会变） | 拔掉换掉时，下面这些不许改 |
|---|---|---|
| 上下文 | 上下文窗口、压缩插件、某家模型 | 交接包、台账、计划卡的写法 |
| 调度 | 叫醒用的插件（事件通路） | 作息表、投递状态机、`passive` 的判据 |
| 通信 | 信件怎么走（文件、队列、MCP） | 信件格式、箱与游标、归档规则 |
| 执行 | 宿主版本、插件层、CLI | 规范、脚本、验收命令 |
| 权限与审阅 | 权限模型（ACL、只读挂载、人工确认） | 「谁改的、怎么拦、出事怎么查」的判据 |

**怎么用（三条，都能被查）**：

1. **动手前问一句**：这次是「往插座上插一个新东西」，还是「把线直接焊死在机器上」？焊死的，改动记录里要写 `临时`，并写清「为什么这次先这么办、什么时候拆」。
2. **没动架构也要记一行**「本次未动架构」——否则半年后没人分得清是守住了，还是压根忘了。
3. **插座只在已经疼过的地方造**：加一个机制前，先写「现在哪里会疼、哪次会话、什么症状」。写不出来的，说明还没疼到该动，先别造。（「计费与配额」就没单列成插座：它现在既没独立兜底、也还没真疼过。）

**两个不做**：不为抽象而抽象（任务模型保持一张表，不上状态机、不上 DAG）；不因为「看起来该有」就加层。

**一个实测**：宿主换版本那一刻，**一个插件都没改**、会话文件格式没变、profile 哈希逐字不动——因为耦合点早就被压到了文件与插座上，而不是「某版本的某个内部实现」。回滚脚本也按这个思路写：先摘掉新插件（旧版本不认识它），再换目录，跑完预检红 0 黄 0 才算成功；不过要说清楚，**真机回滚还没演练过**，只自测过摘插件那一步。

（HSFG 是本库给这套判据起的记法：分层判断与现状归位。它不立项、不排期、不设截止，只在每次要动架构时被引用一次，并被用户定为「版本更新与功能添加的指导思想」。）

## 四段真实协作，逐分钟

制度不是先设计好再执行的。下面四段都是本机真实记录（时间、文件名、命令都能回查），依次是：一段日常闭环、一次判据被判错、一次换线交接、一条被否决的架构提案。

### 一、一封信的十二分钟（2026-11-06 23:38 → 2026-11-07 00:03）

一条业务线的权限档位只到只读：格子改完了，台账却写不进去，只能先暂存、再求有写权的人并账。

| 时刻 | 谁 | 做了什么 | 落了什么证据 |
|---|---|---|---|
| 23:38 | 业务线（只读档位） | 写信给维护线：三处格子已改、三条台账暂存在 `%TEMP%`、索引落后请重跑 | 信 `20261106-233800-from-other.md` |
| 00:00 | 维护线 | 被叫醒（信箱有新信），`digest --for kb` 一次读完整封并归档 | 未读 1→0，信进 `已处理\kb\` |
| 00:00 | 维护线 | 用 `ledger.py add` 把三条正式并进总账，`by` 写「上游业务线」 | 三条 sha256 与发信人的记录逐字相同 |
| 00:00 | 维护线 | 跑 `kb_index.py`＋`kb_check.py` | 14 项全 PASS |
| 00:03 | 维护线 | 回信：删掉暂存文件，别再回填（会重复记账）；下次直接报 `error_code` | 第二封信 |

**这段说明三件事**：① 权限不够不是死路——写不进的账可以暂存，由有权限的人并进去，但 sha 必须能对上；② 「改完了」要有一份能被别人独立复核的证据（字节数＋哈希），不是一句口头确认；③ 顺手把一个坏习惯掐掉（下次别再用暂存这一招），比替人补十次更值。

一个执行细节值得抄走：台账脚本**不许伪造哈希**，只记「并入那一刻的实测值」；发信人记的是六分钟前的数，两边对不上时，差异要写进备注，而不是替对方圆。

### 二、播报被判「没发」，然后判据改了（2026-11-06 15:59 → 16:1x）

维护线换人，按规定发了 A 级播报，并在报到信里说了文件路径。主对话按验收判据去核，结论是**动作三未完成**：`_播报\` 里最新还是前一天那份，全库检索新会话 id 命中数 0。

两边的说法都对，错在判据：

- **对象选错了**：A 级播报 `--scope all` 不投主对话那个箱，主对话在自己的信箱里当然找不到；
- **检索方式错了**：`_索引.md` 每行只存「路径＋标题＋范围」，不存正文——按会话 id 去 grep，永远是 0。

于是改判据（写进规范）：① 报到信必须报「播报文件名＋索引行号」；② 核验按**标题**命中索引，不许用会话 id 去 grep；③ 播报头部同时写「首发」与「最后修订」两个时刻——文件名里的时刻是首发，事后改正文会改 mtime，两个对不上就会被当成「改过没报」；④ 事后只扩写正文，不改标题，否则索引行与交叉引用全要重对。

**这段说明**：被判定不合格时，先分「我做错了」和「判据写错了」两种；判据错了就改判据，并把改法落成可复跑的命令——下次同类争议复跑一次就能自证。

### 三、换一次线：交班信只问三个问题（2026-11-05 交班）

上一任维护线从 2026-11-04 18:42 起接手，干到第二天交班时，用户只给它一句交代：**「让你手上没完成的事全交给下一任，然后你休息。」** 它发出的交班信，正文就是下面这几句（原文，截去与本例无关的编号）：

> 1. 你还没做完 / 正在做的条目：D 或 O 编号 + 具体停在哪一步（比如「只等重启后 24 小时，看某个判定文件不涨」）。
> 2. 你知道但没写进清单的隐患或半成品。
> 3. 这轮必须由我立刻接手的（含：等重启才签的读数项；有没有谁正在你手上交接）。

另附边界，比内容更值钱（原文）：

> 交完之后**请不要再动文件、不要再跑收尾、不要再改清单**——你的院子从现在起归我；工具目录仍归开发线、主对话目录仍归主对话，这两处我们都不代改。
>
> 另：你先前代跑归档的那 22 封，我已告知那条线，它不用再找人。谢谢，休息吧。

接手方也不是「读一遍文件就算认领」。真正管用的是**拿同一份清单回头问原会话**——一问清单外漏掉的活、二问临时决定和没落盘的判断、三问「你现在能不能归档」。对方要明确回一句「无，可归档」或逐条列遗漏，交接才算完；归档由用户点头，不由两个会话互相客气决定。

**验收三条**（都能查）：交接件每一行都有归属（谁做）；原会话那一行标「已交班 → 新 id」；同一件事不许两个会话同时写。查完 `kb_check` 全绿、会话名册里那一行状态变成「已归档」，这一刀才算落地。

### 四、一次架构提议：挡回去的是理由，不是态度（2026-11-07 22:13）

用户提了一个真问题：**「这个问题的根源是文件路径的强制性和台账死记录的强关联……我想从根本上解决，在数据管理上引入数据库（不知道 Python 的 SQLite 行不行）。」** 下面是当时的原对话（节选，已脱敏）。

> **答**：这个判断**说对了一半**，而且对的是最关键的那一半。
>
> **说对的部分**：根因确实是「路径当主键」。当天就有一例——给某个拟建文件加个反引号，自检立刻判死链；反过来，谁改个文件名，台账里那条记录就永久指向不存在的地方。台账存 `path`、播报写 `path`、交接件写 `path`：**所有引用都用路径当主键，而路径是最不稳的东西**。这跟文件多乱没关系，是结构问题。
>
> **我要提醒的部分**：SQLite 治的是另一个病。先看体量——台账 1,842 行 / 391 KB、消息 540 个 md、播报 275 个、文档 1,126 个 md、索引 507 行（11-07 的取数；最新一次是 11-08 的 505 条，见「现在跑成什么样」）。这个量级 `grep` 扫全库是毫秒级，**性能上没有理由上数据库**。SQLite 真正能给的只有三样：唯一约束与事务、跨表关联查询、外键/ID 映射；而「防重复写」已经由单写者、`_认领.tsv`、信箱的 `error_code` 在替代。
>
> **还有一条硬规矩**：这个库自己在一份文件里记着被否掉的提案，包括「索引与台账转 JSON」，再提条件是「出现程序化消费且现有解析失败的具体事故（贴命令与输出）」。现在没有这个事故。按自己的规矩，要么先补这条证据，要么换形态。
>
> **三条路，成本递增**：
> 1. **稳定 ID + 路径映射**（先做）：每份文档一个短 id，`_machine\paths.tsv` 记 `id → 历史路径…当前路径`；台账加 id 列，引用写 id。搬家只改映射，历史账一条不动，约 100 行，**不动任何正文**。
> 2. **SQLite 只做派生索引**（中间）：源数据仍是文本，另建一个库从文本导入，只用来跑跨表查询；丢了随时重建，不进账。
> 3. **SQLite 当唯一真相**（不建议）：8 个脚本重写、双写迁移期、备份要 dump、`git diff` 与「人直接读账」全失效，与「只用文件」的反目标直接冲突。

结果：先做了路 1（稳定 ID + 路径映射），跑通后那条路自己把「改名破引用」这个真疼的地方止住了；路 2 留作随时可试的小规模试跑；路 3 没有做。

这一段最该被读到的地方，不是「我没有采纳」，而是**这套结构在压力下表现出的三种性质**：

- **反脆弱**：提议本身就是一次压力测试。被挡回去时，留下的是可复查的理由（它治哪个病、真疼在哪、现有证据是什么），而不是某个人的脾气。下一次同样的问题再来，可以从这份理由继续，而不是从零开始争。
- **长期记忆**：否决与「再提条件」一起进账本——**连拒绝这个动作本身都被记账**。换人、换模型、隔半年回来看，同一个判断仍能复现；不需要谁记得当时的会。
- **不易变质**：判断的依据是事故证据，不是在场者的偏好，所以它不会随着时间被稀释成「当时好像说过重」。条件一旦出现（真的出现解析失败的具体事故），机制自己会把人叫回来看——这一条不需要任何人守信用。

**这段说明**：拒绝一个提议，理由不能是「我觉得重」。要能指出三件事——**它治的是哪个病、真疼在哪、我们自己的规矩允许它在什么条件下再提**。否决不是把提案扔掉，是把它连同「再提条件」一起记进账本。

## 第 0 步：环境自检（L0）

```bash
python starter/env_check.py
```

它会逐条报 `PASS／WARN／FAIL` 三档，并给每条的补救办法。判读：

- **退出码 0 ＝ python 单进程路线可用**（L1、L2 都能走完）。若 `0700 private dir` 是 WARN，说明你在受限沙箱档位里——不是环境坏了，是档位；要么只跑单进程的 `mailbox_min.py`，要么把会话提到可写档位。
- **退出码 2 ＝ 连 python 路线都不行**（多半是 Python 太旧或 `TEMP` 不可写），先把 FAIL 那几条修掉。

这一步比任何阅读都省时间：同样一份文档，在 `danger-full-access` 的机器上「照做就好」，在默认档位的机器上是「一开跑就 PermissionError」——L0 就是用来提前把这件事说清的。

## 已知不足（不装成已有）

1. **并发只有事后告警，无文件锁**——两条线同分钟写同一文件，靠 sha 核对与冲突告警发现，靠不住运气；
2. **制度面不深**：贡献指南、变更记录、安全策略、行为准则都随包提供了（v1.0.0 起），但都只是短版——没有发布流程、没有版本分支约定、没有安全响应时限；
3. **L3 只是参考实现，不是产品，而且容易把宿主搞崩**——三件自研插件脱敏打成 tgz 放在 `plugins/`，够开发者照着改，但**不承诺装好即用**：`dsh-kbhub` 要先跑 `install.py` 换占位符，另两件要 `dsh plugin add` 再配 profile；作者不再打磨这条路（精力在 L0–L2），装不通就让你的 agent 照 `plugins/README.md` 自己调；
4. **换人多依赖交接包**：交接包越厚，接手越贵；「按需加载」只是候选项，尚未落地；
5. **压缩是单点，无自动降级**——压缩插件被关掉过一次，请求直接冲到上限被拒；
6. **经营面只有记账**：没有预算上限、没有绩效评分、否决账只覆盖提案；
7. **规则靠自觉，缺执行关口**——目前只有一条可数判据（自检 14 项），其余靠人记得；
8. **回滚只演练过一半**：摘插件那一步有自测证据，真机整机回滚没跑过；
9. **没有跨厂商多 agent 协作测试**：全部实测都在单一 harness（DSH `0.2.2-rc.1`）内打转；Claude Code、Codex、GPT 系等不同模型与 harness 混在同一库里协作、互相读信、互相核账，这条**一次都没跑过**——「换 harness」那张表是设计意图，不是实测结论。

- **L3 是参考实现，不再是维护目标；动手前第一件事是做回滚包（`python starter/profile_backup.py save …`），再读 [`docs/L3-动手前必读.md`](docs/L3-动手前必读.md)（我们崩过八次，报错原文都在里面）**：三件 tgz 已脱敏（不含绝对路径、用户名、真会话 id，出厂为占位符形态），但安装、叫醒参数、权限档、侧栏自愈都要人配；这条线**不承诺装好即用**，也不在本包验收范围内。
